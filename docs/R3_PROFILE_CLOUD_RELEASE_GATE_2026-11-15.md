## Implemented, source-only website integration
- New optional **hosted R3 Hypothesis Lab** at `/research/r3-lab/` (the existing Termux/127.0.0.1 offline alpha remains separately functional). Launch links are staged in **Boards** and **Profile**, not a new bottom-nav tab; original premium 14-tab navy/gold dock with arrows is retained. Source labels explicitly state private beta, no automated conclusions and a field-limited Gap Finder (3 incident entries/12 tentative questions, not a global archive audit).
- The strict `scripts/build_public_release.cjs` output now includes only individually reviewed static R3 browser assets, compiled by `scripts/build_r3_hosted_assets.cjs`. The actual browser engine, vault, UI, public-catalogue bridge, styles and version stamp reuse tested offline source. Internal `experiments`, private SQL, recovery documents, screenshots, service secrets and unrelated source directories are **excluded** from public output. Public stage validated at **116 files**.
- New `experiments/r3/hypothesis-cloud.js` reuses the existing Disclosure Desk Supabase project and signed-in session by calling `auth.getUser()`, refusing guest/anonymous sessions. The only online state is a single **manual opt-in encrypted cloud backup per user**. The encrypted envelope is produced by the existing Web Crypto AES-256-GCM vault **in the browser**; no passphrase, original hypothesis content, source narrative or decrypted editor text is uploaded. Plaintext account/profile metadata is restricted to the verified owner UUID, an opaque encryption generation and technical timestamps. Do not represent this as zero-knowledge audited production security.
- `hypothesis-vault.js` retains original `local-vault` IndexedDB key for the standalone localhost ZIP, but hosted R3 uses separately scoped keys `account-<verified UUID>` or `guest-local-v1`. Other signed-in profiles on the same browser do not open each other's local vault slot. Auth sign-out/account switch triggers **immediate decrypted UI clearing and reload**, plus server identity revalidation before each cloud operation.
- Users may explicitly **Back up current encrypted copy**, **Download cloud backup**, **Restore on an empty local vault using their original passphrase**, or **Delete cloud backup** (typed DELETE). Old cloud copies require an affirmative replacement confirmation and conditional generation-match update (optimistic CAS), so another tab's new generation cannot be silently overwritten. Bad passphrases fail before import; the local-vault restore refuses overwriting a present vault. Cloud data isn't autosynchronised, cloud deletion doesn't erase device copies, and no recovery is possible without the original passphrase.
- The remote Supabase browser SDK is pinned to `@supabase/supabase-js@2.119.0`; its exact jsDelivr UMD bytes were downloaded in no-deploy CI and verified with **SRI SHA-384** `uteMfOloLDGt042uDz+xHGF3ym63/WQ6rFq7murQRG8Ih7QrXGEGNtWd8688sb4O`. Hosted R3 uses a restricted CSP, `noindex,nofollow` and no analytics or ad scripts. Existing site configuration and the rest of R2 aren't changed.
- `privacy.html` adds R3's local encryption, optional account backup, retention/deletion and passphrase-recovery limits. Guest and existing W.NE flows remain unchanged.
