# Private quarantine allocation ledger — development-only

This internal schema is a no-deploy candidate, not an active migration, upload API or publicity mechanism. The agreed budget is 250,000,000 bytes across reservations, present quarantined objects and separately reserved approved representation copies. A 5,000,000 byte per-copy upper bound is deliberately conservative. Use the single transactional budget row to serialize concurrent reservations; after-insert accounting avoids consuming bytes for idempotent duplicate inserts. File size and digest are immutable. Do not treat a deletion request, failed scan, expiry, API timeout or an absent metadata row as confirmation that physical bytes are deleted. Keep reservations counted through deletion_pending until the trusted worker confirms the actual Storage API deletion or verified absence; then and only then release capacity. In the SQL state machine this is a trusted timestamp, not itself a verification of the storage provider.

No grant, login role, callable public RPC, browser upload token, storage bucket, direct storage schema mutation, production migration or publication. Even existing service-role API identity has no privileges here. Future trusted storage service needs its own least-privilege, reviewed reservation transactions and cannot rely on client-reported byte counts, user identity or client deletion claims. The actual bucket must be private; reserve verified bytes before any storage copy, enforce one immutable object per reservation, check actual uploaded lengths and SHA-256, no replacements or public visibility before technical validation; clean up via supported Storage API rather than direct database mutations. Roll back reservations only after object absence is independently confirmed. The real Postgres concurrency test uses fictional reservation metadata and disposable network-disabled database; it does not claim end-to-end Storage upload/delete enforcement. Reconcile actual bucket metadata to ledger and block on drift before production. Review live storage capacity and scanner host separately; no extra services or costs authorized.

Official storage guidance: https://supabase.com/docs/guides/storage/schema/design and https://supabase.com/docs/guides/storage/security/access-control.
